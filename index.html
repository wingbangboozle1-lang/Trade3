live data demo environment no API key needed

Five markets, one screen: gas, elections, culture, crypto, golf.

Trade3 reads Kalshi's public Trade API v2 in your browser and turns it into a trader's working dashboard: the biggest-dollar live events per topic, two scrolling alert streams for any ≥ $0.10 contract swing, price charts with seconds-to-days windows, order-book liquidity, resolution tracking and simulated strategies whose results are categorised by trade type.

1 · Two alert streams

Every ≥ $0.10 move posts to the full stream. A second stream applies a published high-ROI screen (price band, move size, spread, dollar volume, book depth) so the noisy tape and the tradeable subset never get mixed up.

2 · Charts you can actually read

X = time (60s → 7d, from 1-minute / 1-hour / 1-day Kalshi candles), Y = contract price in dollars. Amber dots mark ≥ $0.10 steps, and the liquidity panel shows how many contracts rest at each price on both sides.

3 · Trades that prove the plumbing

High-ROI alerts open simulated contracts at the quoted ask. Nothing settles until Kalshi publishes result: yes|no. The portfolio page compares four strategies and slices P&L by topic and by strategy.

What is verified, and how

  • Endpoints — demo and production REST/WebSocket hosts taken verbatim from Kalshi's API Environments page.
  • Field names — yes_bid_dollars, last_price_dollars, volume_fp, result, orderbook_fp … all confirmed against the reference pages before being used, and against live JSON responses.
  • Every series row — re-fetched one by one with scripts/verify_series.py; the report is published on Verification.
  • Nothing inferred — a missing settlement source stays blank. Two crypto series have no published source in the API, and they are flagged rather than filled in.

What is a model, not a fact

  • $ traded = contracts × last price. Kalshi has no dollar-volume field, so this is a disclosed approximation, labelled everywhere it appears.
  • High-ROI screen = five explicit thresholds (price band, move, spread, dollar volume, depth). It is a filter, not a forecast.
  • Strategies = four fixed rules you can read in full on the portfolio page. Demo P&L tests plumbing, not edge.
  • Causes of jumps are never invented. The API carries no news feed, so each contract links to its official settlement source and API record instead.

Suggestions for making this more live and more useful

Shipped in this build

  • Two-speed alerting: raw tape plus a strict screen, with the reason each alert was filtered out.
  • Per-contract chart with legal Kalshi intervals chosen automatically per window, plus candle bodies where OHLC exists.
  • Liquidity table with cumulative depth bars and implied asks derived by the documented $1.00 − bid rule.
  • Resolution tracker that settles simulated trades only on the exchange's own result.
  • Request pacing, 429 backoff, documented host fallback, and an optional user-supplied CORS proxy.
  • CSV/JSON export of every simulated trade so results can be audited outside the browser.

Next, once you have demo keys

  • WebSocket tape: the ticker channel removes polling lag entirely. The handshake needs a signed key (docs), so it cannot live in a public static page — it belongs in a small relay you run.
  • Real demo execution: the repo's kalshi_client.py already signs requests and posts the documented V2 order body.
  • News attribution: needs a news API key; without one, causes would be guesses.
  • Alerts out of the browser: email/Slack on the same threshold once a relay exists.
