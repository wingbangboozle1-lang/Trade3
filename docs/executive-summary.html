Executive summary

Kalshi demo environment · public Trade API v2 · built and verified 2026-11-20.

The one-paragraph version

Trade3 is a static, keyless dashboard over Kalshi's public Trade API v2 covering exactly five topics — gas prices, elections, culture, crypto and golf. It ranks live events by dollars traded, streams two alert feeds for any contract swinging $0.10 or more, charts price against time across seconds-to-days windows, shows order-book depth per price level, tracks each contract until Kalshi publishes a yes/no result, and simulates four fixed trading strategies whose outcomes are categorised by topic and strategy. Every published figure traces to an official Kalshi document or API record; anything unverifiable is blanked and listed for review.

Scope decisions, stated plainly

RequirementHow it is metHonest caveat
Highest-dollar live events, five topics only Events ranked per topic by Σ contracts × last price; markets are classified by their event's category plus the series map, so nothing outside the five topics appears. Kalshi publishes no dollar-volume field; the multiplication is a disclosed approximation (F4).
Alerts on ≥ $0.10 swings, as scrolling chat Two autoscrolling feeds: all swings, and a subset that passes the high-ROI screen. Each message shows the from/to prices, delta, spread and depth. Swing detection needs two observations, so the first refresh of a session never alerts; latency equals the refresh interval (5–60 s).
Track events until resolution (yes/no) Settled markets are polled per series and displayed with the exchange's result; simulated trades settle on that same field. Demo markets often resolve slowly or not at all; an empty table reflects the exchange, not a bug.
Automated simulated trading + strategy analysis Four explicit strategies, fills at quoted ask, P&L by topic and by strategy, CSV/JSON export, plus a Python backtester in the repo. Single-snapshot runs test plumbing, not edge. Demo prices are synthetic by Kalshi's own warning.
Live charts, x = time, y = price, seconds-to-hours Seven windows (60 s → 7 d) with Kalshi's legal candle intervals (1/60/1440 min) chosen automatically, live poll points merged in, ≥ $0.10 steps marked. Kalshi candles lag a few seconds and are capped at 5,000 periods per request — stated in the method page.
Liquidity: contracts available at a price Full bid ladder per side with counts, cumulative depth bars, and implied asks derived as $1.00 − opposing bid. Kalshi returns bids only by design; true resting asks are shown as their implied equivalents.
Links for what may have caused a jump Each alert links the contract's API record, its Kalshi page, and the series' official settlement source (e.g. AAA for gas, CF Benchmarks for crypto). The API carries no news feed. Causation is never asserted — that gap is flagged rather than filled with guesses (F2).

Data provenance

  • REST base: https://external-api.demo.kalshi.co/trade-api/v2, with https://demo-api.kalshi.co/trade-api/v2 as the documented fallback (source).
  • WebSocket: wss://external-api-ws.demo.kalshi.co/trade-api/ws/v2 — documented, but key-gated as a handshake requirement, so the static site polls instead.
  • 37 series across the five topics, each re-verified individually against GET /series/{ticker}.

What I would do next, in order

  1. Add a tiny relay (a few dozen lines) holding your demo key, so the browser can consume the ticker WebSocket instead of polling. That alone takes alert latency from ~15 s to sub-second.
  2. Log alerts server-side from day one — the cheapest way to evaluate whether the high-ROI screen beats the raw tape is a history of both.
  3. Backtest with run_sim.py over several days of demo candles before changing any strategy rule.
  4. Then, and only then, wire real demo orders through kalshi_client.py and compare fills against the simulated ones.
