Flagged for review

Nothing on this page blocks the site. It lists the places where a value could not be confirmed from an official source, where a judgement call was unavoidable, or where a Kalshi record contradicts itself. Unconfirmed values are left blank on the site — never filled in by inference.

F1 “Culture” as a topic — corrected 2026-11-20 by the integration session An earlier revision of this page claimed Kalshi has no Culture category and mapped the topic to Entertainment. That claim was wrong. GET /series?category=Culture answers with 2 series, each carrying "category":"Culture" and "categories":["Culture"] (KXXBANNEDGROK, KXXBANNEDMURRAYHILLGUY1), re-read live at 20:0x UTC. Neither had open markets: GET /markets?series_ticker=KXXBANNEDGROK&status=open → {"markets":[]}. The site now maps Culture to Kalshi's real Culture category and lists Entertainment as a clearly labelled superset (the 8 rows that came from it say so in their via field), so the page is not empty while the real category stays visible. If you want Culture to mean only the 2 official series, delete extraCategories for the topic in docs/assets/app.js — one line. GET /series?category=Culture · open-market check resolved by live re-check
F2 Why a contract jumped ≥ $0.10 Kalshi's public API exposes prices, books, trades and settlement sources — no news feed. Causation cannot be established from official sources, so alerts link the API record, the Kalshi page and the settlement source instead of naming a cause. Automated attribution would need a news API and would still be inference. Market data docs unverified by design
F3 Live WebSocket streaming and real demo orders Both are documented and supported; both require an API key, and the WebSocket requires the handshake itself to be signed. A public static page cannot hold a key without exposing it, so the site polls REST and simulates fills. The signing client in the repo is ready; a small relay you run would close the gap. WebSockets · API keys needs your key
F4 “Highest dollar amount” ranking Kalshi returns volume_fp (contracts), open_interest_fp and prices — there is no dollar-volume field. Events are ranked by contracts × last price. Ranking by raw contract count or by open interest would produce a different order, and neither is more “official”. Get Markets approximation
F5 High-ROI screen thresholds The five rules are published in full and applied exactly as documented. Whether those thresholds isolate genuine opportunity is untested. They are an opinion, encoded and labelled as such — not a validated model. Method → ROI screen heuristic
F6 Strategy results Four rules, fixed fill model (buy the ask), settlement from the exchange's result. Results shown are from demo markets, which Kalshi warns may not reflect real markets. Treat them as a test of the plumbing, not evidence of an edge. Demo environment not evidence
F7 Browser access to the Kalshi API (CORS) Kalshi's docs include browser fetch() examples for the public endpoints. Whether a specific network permits the cross-origin call can only be confirmed from that browser. The dashboard reports the failure and the Method page offers a proxy setting rather than pretending data exists. JS fetch examples verify in your browser
F8 KXBOOKERPRIZE — title vs settlement source Kalshi titles the series “who will win the booker prize”. Its only settlement source is nationalbook.org (National Book Awards), and the contract terms file is BOOKERAWARDS.pdf. These are two different prizes. The row is published exactly as the API returns it; which name is correct cannot be settled from the API, so it is left as-is and flagged here. API record Kalshi metadata conflict
F9 KXLINKPERP and KXSOLPERP — no settlement source Both are Crypto series in the live catalogue, but the API returns settlement_sources: null and an empty contract_url. Their settlement source is therefore blank on the topic page — it is not inferred from the title. If these turn out to be perpetuals rather than event contracts, they may not belong in the topic list at all. KXLINKPERP · KXSOLPERP blank — unverified
F10 Sandbox egress restriction during the build The environment this site was built in could reach the Kalshi API only through its page-fetch proxy, not from the shell. Consequence: every API value was read through an official endpoint and pasted from the response, but automated live re-runs of scripts/verify_series.py must happen from an unrestricted machine. The script is included so you can repeat the check in one command. scripts/verify_series.py (in the repo root) environmental
F11 Unknown query parameters are ignored, not rejected Proved on the demo API this session: GET /markets/trades?market_ticker=<t> returned 200 with trades from other markets, because the documented filter is ticker and market_ticker is not a parameter of that endpoint. Likewise GET /series?limit=3 returned far more than 3 rows — Get Series List documents only category, tags, include_product_metadata, include_volume, min_updated_ts (no limit/cursor at all). Risk to any integration: a mistyped filter looks like a working, filtered query. Mitigated here by filtering the response client-side as well (fetchTrades() in docs/assets/app.js keeps only rows whose ticker matches, and the UI prints how many prints were discarded). Not a Kalshi bug per se — but worth knowing, and worth reporting to Kalshi as a footgun. Get Trades (OpenAPI) · Get Series List (OpenAPI) API footgun — mitigated
F12 kalshi.com page links could not be machine-verified Every API row links to a …/trade-api/v2/… record, which answers from this environment. Links to Kalshi's human site (kalshi.com/markets/<series>) could not be re-read here: the fetch path returned an error for every kalshi.com page tried, while external-api.demo.kalshi.co and docs.kalshi.com answered fine. Those links are kept (they follow the URL pattern an earlier session verified by hand) but are labelled pattern-derived, not machine-verified wherever they appear, and never used as a data source — only as a convenience. Every published value still cites an API or docs URL that answers. docs.kalshi.com/getting_started/demo_env environmental
F13 Most demo contracts are empty and titles carry markdown Live sample (GET /markets?series_ticker=KXBTCD&status=open, 20:0x UTC): the three newest hourly Bitcoin contracts all have last_price_dollars "0.0000", volume_fp "0.00", open_interest_fp "0.00". GET /markets?series_ticker=KXAAAGASM shows the same for two of four strikes, while KXAAAGASM-26NOV30-4.80 carries volume_fp "55571.52". Titles arrive as Will average **gas prices** be above $5.00? — markdown inside a JSON string. Consequences, both handled: (1) “highest dollar amount” is dominated by a handful of contracts, so many topic tables will legitimately be near-empty in demo; (2) the dashboard strips **/*/backticks with cleanTitle() for display only — the API wording is never edited in the data files. gas markets · BTC markets handled, disclosed here
F14 GitHub Pages still cannot be switched on by automation POST and PUT /repos/wingbangboozle1-lang/Trade3/pages both return 403 Resource not accessible by integration for every token this environment is given, and GET /pages returns 404 (no site exists). actions/configure-pages@v5 with enablement: true fails the same way — this is exactly what killed the four deploy runs so far. The deploy job now probes GET /pages first and stops with a written instruction instead of a raw 403, and every check still runs in the verify job, so the site is provably sound while unpublished. One owner click is required: Repo → Settings → Pages → Build and deployment → Source: GitHub Actions → Save. Then re-run the workflow; it will publish docs/.
