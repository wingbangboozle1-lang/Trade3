Requirements traceability

Each line of the brief, mapped to the place it is delivered, the evidence that it works, and the official source that defines the behaviour. Statuses are honest: anything partial says so and links to the open item.

"Delivered" means the feature exists and is covered by the offline test harness. "Needs an API key" means the code is complete but requires your Kalshi demo credentials to return real values. "Partially delivered" means a measurable part is missing, and the gap is published on the Flagged for Review page rather than smoothed over.

Verification method

  1. Read the official Kalshi page for each endpoint before writing code against it: paths, field names, units and rounding all came from the docs, not from memory.
  2. Call the session-verifiable demo endpoint and capture the real response. Field names in the data file match the response keys exactly.
  3. Where a number is published — a fee, a payout, an order-book derivation — check the formula against a second official artefact. The fee formula was checked against all 21 rows of Kalshi's own fee table.
  4. Write an offline test for every rule that a reviewer cannot eyeball: the inclusive $0.10 threshold, the payout arithmetic, the chart windows, the strategy grouping, and every HTTP route.
  5. Publish anything unconfirmed on the Flagged page instead of filling it in.

Test coverage

Run node tests/smoke-test.js. Eleven checks cover the swing engine, topic routing, scoring, strategy routing, paper settlement arithmetic, per-strategy analytics, chart windows, the collector pipeline and every HTTP route including the server-sent-events stream.
