Methodology, sources, and the trade-offs behind them

Everything the site does is traceable to a Kalshi document or to a live API response we re-checked. Where a number is a model rather than a fact, it says so here and in the UI.

Query parameters — what the API actually honours

Checked against the OpenAPI blocks on the official pages and against live demo responses on 2026-11-20. This matters because Kalshi ignores unrecognised parameters instead of rejecting them: a typo in a filter silently returns an unfiltered result set, which can look like real, filtered data.

EndpointDocumented parametersObserved on the demo APIOfficial source
GET /series category, tags, include_product_metadata, include_volume, min_updated_ts. No limit, no cursor. ?limit=3 returned ≥ 8 series — the parameter was dropped. ?category=Gas and ?category=Golf return {"series":null}; ?category=Culture returns 2 series. Get Series List
GET /markets/trades ticker, limit (1–1000, default 100), cursor, min_ts, max_ts (seconds), is_block_trade. Asked with market_ticker=KXAAAGASM-26NOV30-4.80 it answered 200 with trades from KXMARMAD, KXPGATOUR and others — the filter was not applied. So this site filters again in the browser and reports how many prints it dropped. Get Trades
GET /series/{ticker} none (path parameter) Used for the per-row proof link; returns category, categories, tags, settlement_sources[], product_metadata.scope, fee_type, frequency. live example
GET /markets status, series_ticker, event_ticker, ticker(s), limit, cursor, min_ts… A market never carries a liquidity field and never a category — volume/open interest arrive only as fixed-point strings (volume_fp, open_interest_fp, volume_24h_fp). status=open returns records whose own status reads "active". live example

Consequences built into this site: (1) topic membership is decided by categories containment, not by trusting the request filter; (2) liquidity comes from the order book, never from a market field; (3) dollars traded is volume_fp × last price because no dollar-volume field exists (flag F4).

The high-ROI screen, rule by rule

The second alert feed is the first feed with these five filters. They are constants in docs/assets/app.js, so the behaviour is reproducible rather than mysterious.

RuleThresholdWhy
Price band$0.15 – $0.85Below 15¢ a contract can swing 10¢ on almost no money; above 85¢ there is little left to gain.
Move size≥ $0.05The alert already fired at $0.10; this keeps the filter meaningful if thresholds are tuned.
Spread≤ $0.10A move you cannot trade is not an opportunity.
Dollar volume≥ $250 tradedSeparates live contracts from placeholders in the demo book.
Book depth≥ 50 contracts within 3¢ of best bidRough size check against the 10-contract simulated order.

This is a filter, not a model. It has no training data, no backtest claiming an edge, and every message it suppresses says which rule suppressed it.

Chart maths

  • Candlestick period_interval accepts only 1, 60 or 1440 minutes, and a single request may span at most 5,000 periods (docs). The site picks the interval from the window: 1-minute bars up to 24 h, hourly to 7 d, daily beyond.
  • Live poll points are merged with candle closes, so the newest price on the chart is never older than the last refresh.
  • ≥ $0.10 steps between consecutive points are marked in amber — the same threshold as the alerts, so the chart and the feed agree.
  • The Y axis is fixed to $0.00–$1.00 because binary contracts cannot settle outside that range.

Order-book maths

  • Kalshi returns bids only. A YES bid at $0.60 is the same order as a NO ask at $0.40, and vice versa (Orderbook Responses).
  • So the implied YES ask = $1.00 − best NO bid, and spread = implied ask − best YES bid.
  • Arrays are ascending, so the best bid is the last element; the site sorts defensively anyway.
  • An empty array means no resting orders — it is not an error and is never replaced with a guess.

Network options when a browser cannot reach Kalshi

Kalshi's own documentation shows browser fetch() examples against the public endpoints, and this site was built on that basis. Some networks and corporate proxies still block cross-origin requests. If the dashboard reports a fetch failure:

  1. Try the other documented host — the environment switch also swaps the fallback automatically.
  2. Open the page from the deployed HTTPS site rather than a local file path, since file:// origins cannot call the API at all.
  3. If you are behind a restricted network, set a CORS proxy below. It is stored in this browser only and is applied as <proxy><url>; use %s in the pattern to substitute the encoded URL instead. Only use a proxy you trust — it sees your requests, though these are public data.

Requests are serialised (3 at a time, ≥ 90 ms apart) and 429 responses back off exponentially, well inside the token-bucket limits described in Rate Limits.

Trading: simulated by default, executable with your key

The browser engine is simulated. Real demo execution runs from the repo, where a private key can live safely:

# .env  (never commit this file)
KALSHI_API_KEY_ID=your-demo-key-id
KALSHI_PRIVATE_KEY_PATH=./demo_private_key.pem

# what the client posts, matching the documented V2 order body
{
  "ticker": "<market ticker>",
  "side": "bid",                       # bid = buy YES, ask = sell YES
  "count": "1",
  "price": "0.0100",                   # dollars, must sit on the market's price grid
  "time_in_force": "good_till_canceled",
  "self_trade_prevention_type": "taker_at_cross",
  "client_order_id": "<uuid4>"        # idempotency key
}
  • Signing: timestamp + METHOD + path (path includes /trade-api/v2, excludes the query string), RSA-PSS/SHA-256 or Ed25519, base64-encoded, in KALSHI-ACCESS-KEY / -TIMESTAMP / -SIGNATURE (docs).
  • WebSocket handshake signs GET /trade-api/ws/v2 — the socket path, not the REST prefix.
  • A 201 means accepted, not filled: always check remaining_count (docs).
  • Keys are never stored in this repository, never entered into the website, and never sent anywhere but Kalshi.

Known limits, stated up front

  • Polling, not streaming. The public ticker WebSocket requires a signed handshake, which a static page cannot perform without exposing a key. Alerts therefore arrive every 5–60 s depending on your setting.
  • REST data is cached briefly by Kalshi, so a REST price can lag the exchange by seconds (docs).
  • Demo ≠ live. Demo books are thin and synthetic; a strategy that looks fine here has proven nothing about real markets.
  • No news attribution. Causation for a jump is not in the API; the site links sources instead of guessing.
  • Two transports, both labelled. The published site polls Kalshi's public REST API from your browser. Run npm start and the same pages also get a same-origin /live WebSocket (RFC 6455), which pushes alerts instead of waiting for the next poll. The header pill always names the one in use, and neither is ever described as live when it is not.
  • Why the published page cannot use Kalshi's own socket. Kalshi's WebSocket requires a signed handshake — "WebSocket connections require authentication during the connection handshake" (Quick Start: WebSockets). A static page has nowhere safe to keep a private key, so the socket belongs on a server: the collector holds the key, opens the socket, and relays it. That relay now exists in server/ws.js and server/kalshi-ws.js; it reports unconfigured until a demo key is supplied.
  • Static hosting. No server means no shared state: paper trades live in your browser's local storage and are exported as CSV/JSON if you want them elsewhere.
  • Egress. The site is a plain browser app, so it only works where Kalshi's API is reachable and its CORS policy allows the origin — see network for the proxy option if your network blocks it.

How this site is tested

Three independent layers, all of them re-run on every push. If any fails, the deploy job does not run — a broken build cannot reach the live site.

LayerCommandWhat it proves
Static python scripts/check_site.py Every local link, anchor, script and stylesheet resolves; every page closes its HTML; every JS module parses; series.json keeps its contract (39 rows, each with a https://external-api.… proof URL and a category matching its topic); no localhost references leak into the published site.
Logic node tests/logic.test.mjs Order-book maths against the documented example (implied ask = $1.00 − best opposing bid), the ≥ $0.10 alert threshold, the ROI screen's four rejection reasons, legal candle intervals for all seven chart windows, and formatting that renders missing data as “—”, never as a zero.
Render node tests/render.test.mjs The real page scripts run in a headless DOM against recorded Kalshi response shapes: the dashboard must classify only in-scope contracts, detect the reprice as an alert, put it in the high-ROI feed, open a simulated trade, draw the book and chart, and honour #ticker deep links; the portfolio must compare four strategies; a topic page must keep its proof links and stay inside its own topic.

The render layer caught two real defects during this build: the client kept a bare hostname as its base URL after the first successful call (so every later request lost its scheme and /trade-api/v2 path), and selecting a contract threw in engines without scrollIntoView. Both are fixed.
